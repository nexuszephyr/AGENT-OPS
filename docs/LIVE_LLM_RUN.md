## Findings for #12

Every check passed, so these come from the per-turn traces (tool sequences, replies, latency), not from failed checks. Written by hand for the 2026-10-24 06:35 UTC run above; `live_llm_check.py` keeps this section (and marks it possibly stale) when it rewrites the report.

- **A turn that starts the plan uses up the whole 8-tool-call budget.** A3 used exactly 8 calls in both runs (`update_profile → check_eligibility → pick_next_question → plan_actions → raise_request ×2 → fill_form ×2`). Of the two `fill_form` calls, one queued PMFBY and the other queued nothing. No nominee had been given yet, so it most likely returned `NEEDS_INFO`, but the harness doesn't record tool args or non-error results, so this isn't confirmed. PMJJBY/PMSBY/APY waited for A4. With one more product or one retry, the turn would hit the cap before queueing everything. *Evidence:* A3, runs 1 and 2. *Fix:* have `plan_actions` list each step's `missing_mandatory` fields, and tell the model not to call `fill_form` until those are known. Also put the profile in `context_block` so turns don't open with `fetch_customer` (12/20 turns did).
- **The model invents question ids to ask the officer for form fields.** It asked `NOMINEE_DETAILS`, `Q_NOMINEE`, `NOMINEE` and `ssy_girl_child`, none of which are in the catalogue. `_vet_question` dropped each one (5 `question_replaced` events in 20 turns). The guardrail held, and the request still showed up in `to_officer`, but the `question` field is being misused. *Evidence:* A3 (both runs), C2 (both runs), B1 run 2. *Fix:* the prompt should say `question` is only for ids returned by `pick_next_question`, and that form fields (nominee, girl child name) are asked for in `to_officer`. Or add a `needs_from_officer: [field]` field to AgentReply.
- **A rejection fixes only the rejected form, not its siblings.** After "Nominee name is Anjali, not Anjeli", the agent revised PMJJBY. It left PMSBY (queued in the same turn with the same nominee) still saying "Anjeli", and asked the officer to reject that one too ("I can't see its payload"). *Evidence:* B2, both runs. *Fix:* put the session's other PENDING_APPROVAL payloads in `REVISION_PROMPT`, and tell the model it can refill a pending draft with `fill_form` (which already uses `replace_pending`). Rejected items still go only through `revise_item`.
- **What the officer reads says UNKNOWN while the panel shows VERIFY_MANUALLY.** On "Not sure", the reply text said "APY stays UNKNOWN and is marked for manual verification". During the turn the tools still report UNKNOWN, because the pending question is only cleared in `loop._finish`, after the model has replied. *Evidence:* D2 run 2. *Fix:* rebuild `highlights` from the final `state_view` after `_finish`, or clear the pending question as soon as the model signals it is unanswered. This also matters for the "report statuses exactly" rule.
- **The demo script never gives the girl child's name, so SSY is never queued for Priya.** SSY is ELIGIBLE, but `fill_form('SSY')` needs `girl_child_name` and `girl_child_dob`. The model asked for them (and in B2 asked whether Anjali is the daughter), but DEMO.md's "Forms are generated" step implies SSY appears without that. *Evidence:* B1/B2, both runs. *Fix:* add the daughter's name to the officer's line in DEMO.md §1 (e.g. "Daughter Anjali, born 2020-03-14, for SSY"). Alternatively, make the planner's checklist show the SSY fields as needed.
- **Turns are slow enough to notice on stage.** Median 9.1 s; A3 took about 19 s in both runs (8 tool round-trips), and one A2 took 30.4 s on only 3 tool calls (API latency spike). *Evidence:* latency table. *Fix:* same as the first bullet (fewer round-trips), plus a visible "agent is working…" spinner in the UI. Consider a smaller/faster model for plain tool-routing turns.
- **The crop confirmation is enforced only by the prompt.** The model correctly didn't set `grows_notified_crop`/`in_notified_area` on "Ramesh says…", and did set them on "Officer here: confirmed…" (2/2). The only thing separating the two is the model reading the wording. *Evidence:* A2/A3. *Fix (low priority):* route the notified-list confirmation through the officer fact form (`POST /facts`, actor `officer`) and have `update_profile` reject those two fields from the agent.
- *Unverified:* in D1 run 1 the model called `update_profile` on a bare "hello". Outcomes were correct (D2 passed), but the harness doesn't capture tool arguments, so what it tried to record is unknown. *Fix:* log tool args and `fill_form` statuses in the harness trace on the next run.
